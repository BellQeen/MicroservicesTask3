### Задача 1: Обеспечить разработку
Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

Предлагаемое решение: GitLab CI/CD + GitLab Runner + Docker Registry.

GitLab используется для хранения исходного кода в отдельных Git-репозиториях для каждого микросервиса, а также для управления процессом разработки.

GitLab CI/CD обеспечивает автоматическую сборку и тестирование приложений при изменении кода, а также позволяет запускать сборки вручную с указанием параметров. Конфигурация сборок описывается в .gitlab-ci.yml, где можно создавать шаблоны, использовать различные конфигурации сборки и добавлять пользовательские команды.

GitLab Runner выполняет сборки и тесты в Docker-контейнерах. Агенты можно развернуть на собственных серверах и настроить параллельное выполнение задач. Собранные Docker-образы сохраняются в Container Registry.

Секретные данные хранятся в защищённых переменных CI/CD с ограничением доступа.

Обоснование выбора: GitLab объединяет управление Git-репозиториями и CI/CD в одной системе. GitLab Runner обеспечивает гибкое масштабирование сборок, а Docker позволяет создавать воспроизводимые окружения для сборки и тестирования приложений.

### Задача 2: Логи
Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

Предлагаемое решение: ELK Stack + Filebeat + Kafka.

Filebeat устанавливается на каждый хост и собирает логи микросервисов из stdout и stderr. Для надёжной доставки данные передаются в Kafka, которая буферизует сообщения и позволяет переживать временные сбои последующих компонентов.

Logstash получает сообщения из Kafka, обрабатывает их и передаёт в Elasticsearch для хранения и индексирования.

Kibana предоставляет разработчикам интерфейс для поиска, фильтрации и анализа логов. В Kibana можно сохранять поисковые запросы и предоставлять коллегам ссылки на них. Доступ к логам ограничивается с помощью ролей и прав пользователей.

Для повышения надёжности можно настроить дисковые очереди, подтверждение доставки, репликацию Kafka и резервное копирование данных.

Обоснование выбора: Elasticsearch обеспечивает быстрый поиск по большим объёмам логов, Kibana предоставляет удобный интерфейс анализа, Filebeat позволяет собирать данные без существенных изменений приложений, а Kafka повышает устойчивость системы к временным сбоям.

### Задача 3: Мониторинг
Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре. Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:

- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

Предлагаемое решение: Prometheus + Grafana + Node Exporter + cAdvisor + Alertmanager.

Node Exporter собирает метрики операционных систем: загрузку CPU, использование RAM, состояние дисков и сетевых интерфейсов. cAdvisor собирает метрики потребления ресурсов Docker-контейнерами. Для сбора специфических метрик микросервисов используются встроенные средства инструментирования приложений или специализированные экспортёры.

Prometheus периодически собирает и хранит метрики. С помощью PromQL можно выполнять запросы, фильтровать данные и агрегировать показатели по хостам и сервисам.

Grafana используется для создания настраиваемых панелей мониторинга. Alertmanager обеспечивает маршрутизацию оповещений о неисправностях и превышении установленных порогов.

Обоснование выбора: Prometheus обеспечивает сбор и обработку метрик, Grafana предоставляет гибкие средства визуализации, а экспортёры позволяют контролировать состояние инфраструктуры и отдельных микросервисов. При необходимости система масштабируется за счёт дополнительных экземпляров Prometheus и специализированных решений для долгосрочного хранения метрик.
